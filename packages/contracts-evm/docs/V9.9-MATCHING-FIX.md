## Issues Identified

### Issue 1: Cancel Button Persists After Cancellation (Low)

**Symptom:** Cancel button remains visible after successfully cancelling an order.

**Root Cause:** React Query cache returns stale data, or race condition between chain state update and refetch.

**Code Path:**
```
Pro.tsx:handleCancelOrder()
  → writeContractAsync('cancelOrder')
  → waitForTransactionReceipt()
  → onRefresh()
  → useUserOrdersDirect.refetch()
```

**Fix:**
- Option A: Add optimistic update to immediately remove order from UI
- Option B: Add delay before refetch to ensure chain state is updated
- Option C: Use `queryClient.invalidateQueries()` with proper stale time

**Files to modify:**
- `apps/web/src/pages/Pro.tsx` (handleCancelOrder)
- `apps/web/src/hooks/v8/direct/useUserOrdersDirect.ts` (query config)

### Issue 2: Claim Button Shows After 0 Claim (Medium)

**Symptom:** "Has fills to claim" badge persists after claiming returns 0 shares.

**Root Cause:** UI checks `filledShares > 0` but `filledShares` includes already-claimed amounts, not just pending.

**Code Path:**
```typescript
// useUserOrdersDirect.ts:118-126
const pendingShares = pendingFills?.[0] ?? 0n;
const totalFilledShares = order.filledShares + pendingShares;
// ↑ This merges pending into total, losing the distinction

// Pro.tsx:407
const hasPartialFills = orders.some(o => o.filledShares > 0n && o.active);
// ↑ This checks total, not pending
```

**Fix:**
1. Keep `pendingShares` as a separate field in the RangeOrder interface
2. Update UI to check `pendingShares > 0n` instead of `filledShares > 0n`

**Files to modify:**
- `apps/web/src/hooks/v8/direct/useUserOrdersDirect.ts`
  - Add `pendingShares` field to RangeOrder interface
  - Return it separately from `filledShares`
- `apps/web/src/pages/Pro.tsx`
  - Update `hasPartialFills` logic to check `pendingShares`
  - Update order display to show pending vs claimed separately

### Issue 3: No Autoclaim on New Interaction (Medium)

**Symptom:** Users must manually click CLAIM; pending fills aren't auto-claimed when placing new orders.

**Root Cause:** Frontend never calls `batchClaimFills` or `claimFillsFor` automatically.

**Contract Capability (already exists):**
```solidity
// TickBookPoolManager.sol:746-766
function claimFillsFor(bytes32 marketKey, uint256 orderId) external;
function batchClaimFills(bytes32 marketKey, uint256[] calldata orderIds) external;
```

**Fix:**
Add autoclaim before each user interaction:

```typescript
// Before placing new order
const pendingOrderIds = userOrders
  .filter(o => o.pendingShares > 0n)
  .map(o => o.orderId);

if (pendingOrderIds.length > 0) {
  await writeContractAsync({
    address: contracts.TickBook,
    abi: V9_ABIS.TickBookPoolManager,
    functionName: 'batchClaimFills',
    args: [marketKey, pendingOrderIds]
  });
}
```

**Files to modify:**

  - Add autoclaim in `handleSubmitOrder` before placing order
  - Add autoclaim in `handleCancelOrder` (already calls `_claimInternal` in contract)
- Consider: Create `useAutoClaim` hook for reusability

### Issue 4: Matching Mechanism Bug (CRITICAL)

**Symptom:** Makers receive fills at prices outside their specified range. Orders show >100% fill. New orders don't sweep from worst-to-best price.

**Example 1 (from chain data):**
- Order 1: BUY YES @ 35.2%-55.0% → received 10,016 shares (100.2%)
- Order 5: SELL YES @ 0.1%-99.9% crossed at tick 698 (69.8%)
- Order 1 should NOT have been filled (698 > 550)

**Example 2 (correct behavior):**
```
Existing: BUY 100 @ 30%-35% (tick 300-350)
New:      SELL 200 @ 35%-45% (tick 350-450)

Expected:
- SELL sweeps from WORST price (tick 350) toward BEST (tick 450)
- Overlap exists at tick 350
- Fill 100 shares at tick 350
- BUY order fully filled, removed
- SELL order: 100 filled, remaining 100 resting @ ~35%-45%
```

**Root Cause:** `_tryCross` has TWO bugs:

1. **Wrong sweep direction:** Picks single `crossTick` instead of sweeping from new order's worst price
2. **Pro-rata distribution:** Uses global `_totalLiquidity` instead of per-order fills

**Correct Sweep Direction:**
```
SELL order: sweep LOW → HIGH (worst ask → best ask)
  - Seller wants highest price
  - Start at tickLower (floor/worst), sweep up toward tickUpper

BUY order: sweep HIGH → LOW (worst bid → best bid)
  - Buyer wants lowest price
  - Start at tickUpper (ceiling/worst), sweep down toward tickLower
```

**Problematic Code (TickBookPoolManager.sol:1047-1094):**
```solidity
// Bug 1: Single crossTick instead of sweep
if (newOrder.outcome == 1) {
    crossTick = bestOpposite > newOrder.tickLower ? bestOpposite : newOrder.tickLower;
} else {
    crossTick = bestOpposite < newOrder.tickUpper ? bestOpposite : newOrder.tickUpper;
}

// Bug 2: Pro-rata to ALL makers regardless of overlap
crossedShares = newOrderTotal < oppTotalLiq ? newOrderTotal : oppTotalLiq;
_fillGrowthGlobalX128[marketKey][opposite] += (crossedShares * Q128) / oppTotalLiq;
```

**Correct Behavior:**
1. New order sweeps from its WORST price toward BEST price
2. At each tick, match against overlapping opposite orders
3. Fill individual orders directly (not pro-rata growth)
4. Stop when new order fully filled or no more overlap
5. Remaining unfilled portion becomes resting order

**Fix Approach: Reuse `_fill()` Logic**

The `_fill()` function already sweeps tick-by-tick correctly for market orders. `_tryCross` should:
1. Determine sweep direction based on new order's outcome
2. Call `_fill()` with the overlapping range
3. Credit fills to individual orders, not global accumulator

**Pseudocode:**
```solidity
function _tryCross(marketKey, newOrderId) {
    RangeOrder storage newOrder = _orders[marketKey][newOrderId];
    uint8 opposite = newOrder.outcome == 0 ? 1 : 0;

    // Find overlap between new order and opposite liquidity
    (uint16 overlapLow, uint16 overlapHigh) = _findOverlap(
        marketKey, newOrder, opposite
    );

    if (overlapLow > overlapHigh) return (0, 0, 0); // No overlap

    // Sweep from new order's WORST price
    bool sweepUp = newOrder.outcome == 0; // SELL sweeps up, BUY sweeps down

    // Use _fill logic to sweep through overlapping ticks
    (crossedShares, cost) = _fillRange(
        marketKey, opposite, overlapLow, overlapHigh,
        newOrder.sharesTotal, sweepUp
    );

    // Credit new order owner directly
    vault.creditOutcome(market, newOrder.owner, newOrder.outcome, crossedShares);
    newOrder.filledShares += crossedShares;
}
```

**Files to modify:**
- `packages/contracts-evm/contracts/TickBookPoolManager.sol`
  - Rewrite `_tryCross` to sweep from worst price
  - Add `_findOverlap()` helper
  - Add `_fillRange()` or reuse `_fill()` with range bounds

**Testing required:**
- Unit test: SELL sweeps low→high, BUY sweeps high→low
- Unit test: Partial fill leaves resting order at correct price
- Invariant: maker only receives fills within their tick range
- Invariant: fills happen at overlap prices, not arbitrary tick
